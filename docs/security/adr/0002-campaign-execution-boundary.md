# ADR 0002: Campaign execution boundary

Status: proposed, with a host-side lifecycle prototype. No runtime migration or deployment has occurred.

## Decision context

`PrepareExecPrivilege` shares every task and session run directory with one executor GID and configures one executor UID/GID for Bash shims, custom tools and file tools. `prepareExecHome` creates one `<data>/exec-home` and `execHomeEnv` supplies that path to every executor. Spill directories are readable by the same group. A process running under this identity can therefore read or modify another run directory through ordinary filesystem permissions. The existing privilege drop protects the root-owned control plane, but it does not isolate campaigns from each other. An opt-in synthetic root-capable Linux probe on 2026-11-27 observed cross-campaign file read/write, HOME reuse and process signaling under this identity. The probe confirms exposure; it does not implement or verify isolation.

The custom-tool launcher formerly used `SysProcAttr.Credential` without setting `no_new_privs`. A root-capable regression observed `NoNewPrivs: 0` in the Python child. It now uses the same drop shim as MCP, with an explicit keep list for its session and scalar parameter variables. The regression observes `NoNewPrivs: 1`; focused normal/race tests, environment allowlist tests, `go vet`, Windows cross-compilation and the full PostgreSQL-backed server suite passed in disposable containers. This strengthens the process privilege boundary, but every campaign still shares the same executor identity and HOME.

The supported-platform check now rejects the privilege drop on non-Linux Unix hosts before setup; those hosts cannot provide the Linux `no_new_privs` guarantee. A macOS server test binary cross-compiled after this change. No macOS runtime acceptance is claimed.

## Docker Desktop feasibility probe

On 2026-11-27, a disposable `artex:local` container with no network or operational mounts could not create user, PID, network or mount namespaces with `unshare`; each attempt returned `Operation not permitted`. This is a runtime constraint of the tested Docker configuration, not a universal Linux result. An in-process broker that requires these namespace operations cannot be enabled in the current container.

Two separate disposable sibling containers were then started with `--network none`, a read-only image, private tmpfs at `/campaign`, no capabilities, `no-new-privileges`, and CPU, memory and PID limits. Their PID, mount and network namespace identifiers differed. A marker written in A's private tmpfs was absent in B; B could neither see nor signal A's host PID. The probe used synthetic data and did not mount any operational ARTEX volume. The existing `artex:local` image declares `/app/data` and `/app/keys` volumes, so Docker created distinct empty anonymous volumes for these probes; they were inspected and removed with the probe containers. A production execution image must avoid or explicitly override those image-declared volumes.

This proves only that Docker Desktop can supply separate local container boundaries under the tested options. It does not prove ARTEX routes any executor through them, that approved network traffic works, that a compromised process cannot exploit a kernel flaw, or that lifecycle and artifact exchange are correct. The implementation path is a dedicated trusted broker outside the ARTEX server and agent containers. It must own container creation and lifecycle, accept only opaque campaign handles and fixed reviewed image/policy choices, and expose no Docker daemon socket to the server or agents. Engine access in a broker is host-powerful and requires a separate credential and API review before deployment.

## Host-side lifecycle prototype

The broker now also rejects a running container whose effective Docker configuration adds host PID, IPC, UTS, cgroup or user namespace modes, devices, supplementary groups, extra hosts, links, inherited volumes, published ports or security options beyond `no-new-privileges`. A pre-fix unit regression accepted each of these mutated inspect records. Post-fix package race tests and vet passed, and a cross-compiled Windows smoke test created and removed a broker sandbox from the local pinned ARTEX image on Docker Desktop. This attests the fixed `--network=none` prototype more completely; it does not make an untrusted ARTEX server process safe to hold the Docker socket, and no executor has been routed through the broker.

`sandboxbroker` now provides an in-memory campaign-to-handle registry and a Docker CLI engine for a trusted host-side process. The broker accepts a pinned image digest, allocates a random opaque handle and container name, creates one container per campaign, starts it, checks the effective Docker policy, and removes it by handle. A failed start or policy check triggers removal. Docker creation uses no bind mount, no network, a read-only root, dropped capabilities, `no-new-privileges`, a fixed non-root user, CPU/memory/PID limits, and private tmpfs paths. HOME, TMPDIR and the XDG config, cache, data, state and runtime paths point inside those private tmpfs paths. The runtime directory is created with mode 0700; policy verification checks each environment path. The `/app/data` and `/app/keys` tmpfs overrides prevent the current image's declared volumes from becoming anonymous volumes or exposing an operational mount. A local disposable container probe confirmed these paths were tmpfs and `docker inspect` reported no `Mounts` entries. Unit tests exercise handle lifecycle and reject an unexpected image volume, bind mount, bridge network or shared XDG cache; `go test -race` and `go vet` passed for the package.

This is deliberately not wired into the server or agents. It does not run ARTEX tool flows, mediate network egress, exchange artifacts, authorize operators, persist handles across a broker crash, or prove teardown after host failure. The prototype's Docker Engine access remains host-powerful. Docker policy verification and failure recovery need further adversarial review before production use. The current ARTEX deployment still uses the shared executor. The prototype is not a security acceptance gate and must not be reported as remediating ARTEX-001, ARTEX-004, or ARTEX-005.

A Linux-only `cmd/artex-sandbox-broker` executable now serves a small local control API through `sandboxbroker.ServeUnix`. It requires an explicitly supplied pinned image, absolute Docker CLI path and `broker.sock` path beneath root-owned, non-writable ancestors. The socket is mode 0600, and the listener checks kernel `SO_PEERCRED` UID 0 before accepting a connection. The internal HTTP handler accepts only create, bounded run and remove operations through opaque handles, rejects unknown JSON fields and oversized bodies, and suppresses raw Docker and failed-command output in generic errors. A normal service shutdown drains requests, removes the broker's registered sandboxes and unlinks the socket. A disposable Linux test demonstrated a root request and rejection of UID 10001 even after test-only permission relaxation, followed by sandbox removal; race tests, vet and a Windows fail-closed cross-build passed. The handler is not exported for arbitrary TCP use. The executable has not been started or mounted into the operational ARTEX deployment. Docker user-namespace-remapped credentials, server-to-broker authorization, scoped result transfer, broker restart recovery and all tool routing remain unverified.

`scripts/test-broker-cross-container.ps1` now verifies the socket boundary between separate Docker Desktop containers using the actual `ServeUnix` implementation with a fake engine. A root client in one container created a synthetic campaign handle through the private named-volume socket. After test-only relaxation of the socket file mode, a UID-10001 client in another container connected but received a reset before any HTTP response, proving the peer-credential check applies across those containers. A stop marker triggered graceful shutdown; the fixture checked its synthetic sandbox removal and socket unlink, then removed all test containers and the named volume. This closes the cross-container socket feasibility check only. The fixture does not start the Docker CLI engine, mount a control socket into ARTEX, bind operator/task authorization, exercise a real executor, or prove behavior under Docker user namespace remapping.

`Dockerfile.broker` packages only a CGO-free broker binary and the statically linked Docker CLI copied from a digest-pinned official image into a scratch runtime. A disposable local build produced a 41 MB image. `scripts/test-broker-docker-control.ps1` then ran that image with no network or writable root, the Docker socket mounted only in the broker fixture, and a separate private volume for its control socket. Through the real Unix API and Docker CLI engine it created two synthetic campaign sandboxes from the locally pinned ARTEX image, executed one bounded command, verified the sandboxes had no network or persistent mounts and could see neither broker nor Docker socket, removed one by handle, and removed the other on graceful stop. The test removed its named volume and containers. The operational `artex-artex-1` container was read-only inspected and still had only `/app/data`, `/app/keys` and `/app/skills` mounts; no Docker socket was added. The scratch image and this test are local validation artifacts, not a deployed service. Docker socket possession remains host-powerful, and a production image, policy for service credentials, task authorization, artifact transfer, crash recovery and every executor route still require acceptance before enablement.

The control-plane `sandboxbroker.Client` now speaks only to an absolute `broker.sock` under root-controlled ancestors. It checks the socket type, root owner and mode 0600 before construction and every new connection, never uses a TCP proxy or follows redirects, bounds responses and omits opaque handles from transport errors. Synthetic Linux tests cover create/run/remove, an unavailable broker, a weakened socket mode and a symlink substitution; the package race suite and vet passed, and the client cross-compiled for Windows with its socket validation failing closed there. The HTTP service request cap was raised to 512 KiB so a valid 64 KiB command remains accepted after JSON escaping; a full-size control-character regression passed. This client is not connected to ARTEX. `agent.RunInfo` carries optional attribution and is not sufficient authority to create or select a campaign sandbox; the server must verify the live task and operator scope against the database before issuing broker calls.

Every new broker sandbox carries an owner label in addition to its per-container ownership token. `DockerEngine.Verify` and failed-create cleanup require both labels to match the trusted broker's `Spec`. The Linux broker command persists the owner in a root-owned mode-0600 file beside its private control socket and holds an exclusive lock for its lifetime. A root-only write-ahead journal records the random name and token before Docker creation. On restart, recovery removes a journaled container only after checking its token, owner, name, pinned image and fixed isolation policy; ambiguous resources fail startup and remain for review. A disposable Docker crash-restart test passed while a foreign-labeled fixture survived. Handles are intentionally invalid after restart, and production recovery and all ARTEX execution paths remain unverified.

After the socket validator refactor and client addition, the scratch broker image was rebuilt locally and `scripts/test-broker-docker-control.ps1` passed again against the real Docker Engine. The validation image and disposable fixtures were removed. The Windows result is a compile check; the non-Linux rejection is enforced by the source stub, not a Windows runtime test.

The Docker adapter now attaches a separate random ownership label to each container and checks that label and the full container ID before cleaning up a failed `docker create`. A deterministic unit regression rejects removal of a different container occupying the requested name; an opt-in Docker Desktop collision test confirmed the foreign fixture survived. The opt-in `TestDockerBrokerSmoke` was cross-compiled with Go 1.26.11 and passed natively on Windows against the local image digest. It created, verified and removed one disposable Docker container; no sandbox container remained afterward.

An opt-in broker-created two-campaign Docker Desktop test now passes with synthetic markers. A and B wrote concurrently as UID 10001 through opaque broker handles; each retained its own `/campaign`, HOME and XDG markers and could not see the other's private marker. B could not signal A's host PID from its PID namespace. After A was removed and created again, its `/campaign`, HOME and XDG markers were absent. The test used internal container IDs only to inspect the host PID; no ARTEX tool or server request used the broker. It does not cover browser profiles, command-output spills, explicit artifact exchange, authorized network traffic, crash recovery or adversarial host access.

The broker now exposes `Run` for a bounded shell command through an opaque handle. It verifies the effective Docker policy before each command, serializes operations within a sandbox while allowing separate campaigns to run concurrently, and limits execution to 30 seconds and combined output to 1 MiB. Cancellation, output exhaustion or failed policy verification poisons and removes the sandbox; if removal fails, the handle remains unusable and can be retried for removal. Unit race tests cover normal command errors, unsafe retirement, stale handles and cross-campaign concurrency. The two-campaign Docker Desktop test now uses `Run`, and a separate cancellation test observed the container and handle removed after a synthetic `sleep` was cancelled. The operation has no stdin, terminal, background-process tracking, credential injection or artifact exchange, and it is still not connected to ARTEX. A 30-second tool limit is a prototype safety cap, not a production budget for legitimate long-running jobs.

The prototype now reserves a per-sandbox `/artifacts` tmpfs with a 64 MiB limit and root-owned mode 0755. The fixed executor UID can read files placed there by a trusted process but cannot create or replace entries. Docker policy attestation requires the exact mount ownership and permissions; recovery test fixtures use the same policy. An initial Docker Desktop smoke test used a synthetic root-seeded file to exercise read access, write and rename denial, and absence from another campaign. Root access to Docker remains host-powerful; the test-only direct root seeding is not an application interface.

The broker now accepts one file up to 16 MiB through a root-only Unix API bound to an opaque sandbox handle. It rejects path separators and special names, streams bytes through a fixed `docker exec -i` root command into a mode-0700 staging directory under the private tmpfs, changes the staged file to mode 0444, and renames it into view only after the input closes successfully. The broker retires the sandbox on a transfer or policy-verification failure. The client checks the SHA-256 returned for the accepted bytes. Unit race tests, vet, a two-campaign Docker Desktop smoke test, and the packaged broker's Docker-backed Unix API fixture passed with synthetic data. The first attempt using `docker cp` failed because Docker rejects that operation on a read-only container root even when the destination is tmpfs; stdin transport passed without weakening the container policy. This provides a bounded execution-side delivery primitive, not an ARTEX server ingestion path, a durable artifact store, a binding from file bytes to task authorization, or integration with existing tool paths. Retried names, crash behavior during publication, and use by a live task require further validation. ARTEX-001, ARTEX-003 and ARTEX-005 remain open.

The Docker transfer now checks the staged file's SHA-256 against the broker's input digest before the rename. A native Docker Desktop regression changed the bytes sent to `docker exec -i` after that digest was computed: the command rejected publication and the broker retired the sandbox. The packaged broker API fixture also passed with an unmodified synthetic artifact. This verifies rejection of a corrupted transfer in the tested image; it does not establish a durable source-of-truth store, campaign authorization or live tool routing.

An internal `taskSandboxController` now binds an opaque broker handle to a live task ID and exploration ID verified from the task registry. It refuses missing or changed rows, paused, queued or terminal tasks, and chat-session attribution; it uses the engine's deletion admission barrier and does not accept a model-supplied handle. It serializes operations within one task, keeps two tasks separate, and retains a failed removal for retry. Focused race tests and vet passed with synthetic backends. The task-delete handler now removes a bound sandbox after PostgreSQL commits and the engine stops, or reports a cleanup warning while retaining a failed removal for retry. PostgreSQL-backed normal and failure/retry tests passed with synthetic task rows and a fake broker. No runtime tool path calls this controller, and no operator execution grant or production broker connection has been installed. The current shared executor remains active.

## Execution handoff inventory

| Path | Current entry point | Migration requirement |
| --- | --- | --- |
| Planner, worker and main agent Bash | `agent/planner.go`, `agent/worker.go`, `agent/mainagent.go` compose Norma default tools; `server/execpriv_unix.go` places the Bash drop shim on `PATH` | Replace the SDK process launch with a broker-backed tool for every task run, including background jobs and cancellation. A task ID alone is not a verified campaign grant. |
| Chat Bash | `agent/chat.go` composes the same default tools but records a session ID with task ID zero | Assign an explicit chat trust domain and sandbox lifecycle; do not silently attach a chat session to a campaign. |
| Interactive shell | `server/assembly.go` exposes Norma `ShellSessionTools` to enabled agents; the same Bash shim currently supplies its identity | Keep stdin, terminal state, process groups, close and cancellation semantics inside one authorized sandbox. |
| Custom command and Python tools | `server/customtool.go` sends command tools through Norma Bash, while `execPython` starts the interpreter directly after writing a script | Route both launch paths and script/parameter transfer through the broker. The server must not execute arbitrary campaign code directly. |
| Stdio MCP | `server/assembly.go` and `server/mcpdiscover.go` start configured commands, including global discovery and agents' per-run clients | Decide whether discovery is non-executing metadata or runs in an isolated scope; carry stdio streams and approved credentials through a scoped broker channel. |
| File tools | `agent/filetools.go` runs Read/Write/Edit/MultiEdit/LS/Glob/Grep inside the server under a temporary filesystem identity | Move campaign file access to a sandbox-facing file API or a separately authorized artifact store; a host `os.Root` over a shared run tree is not campaign isolation. |
| HTTP MCP, WebFetch and custom HTTP | `server/mcpdiscover.go` creates HTTP/SSE clients; `agent/chat.go` and `server/customtool.go` provide additional direct network paths | Enforce the same per-campaign target grant in a network gateway, including redirect and DNS decisions. Process isolation alone cannot enforce ARTEX-004. |

`agent/runinfo.go` carries task, exploration, intent or chat-session attribution to tool assembly. It is optional context, not an authorization token. The broker cannot infer campaign scope from it without a server-side operator grant and a verified task-to-campaign mapping. Startup MCP discovery and chat have no task scope, so both need explicit handling before an isolated mode can be enabled.

## Proposed boundary

Introduce a trusted campaign execution broker that owns a `SandboxHandle` for each campaign. The handle carries an opaque ID, the authorized campaign and operator scope, private filesystem and process namespace references, network policy reference, resource limits and lifecycle state. The server must use that handle for every Bash, interactive shell, background task, Python, custom-tool and stdio MCP launch, and for file-tool operations. No tool receives a raw identity, host path or namespace selector from an LLM or imported document.

The broker creates a separate Linux execution sandbox for each campaign with a distinct writable filesystem, private HOME, XDG directories, TMPDIR and browser profile, independent process namespace and limits. It mounts approved binaries and read-only resources explicitly. Credential injection is per operation and scoped to the handle; it is never inherited from the server's full environment. Network access follows ADR's future campaign policy design and fails closed when enforcement is unavailable. The broker mediates controlled artifact exchange; the shared workspace is not a private campaign store.

The control plane retains keys, database credentials, archive staging and evidence staging outside every executor mount. Run output and spills are bound to a campaign identity and cannot be opened through another handle. Sandbox teardown revokes the handle, stops remaining processes and removes only its ephemeral state. Persistent campaign artifacts survive through a separately controlled store. Reuse requires a new handle and a clean ephemeral filesystem.

## Migration and validation gates

1. Inventory all launch paths and filesystem consumers, including third-party Norma background tasks, MCP servers and restored campaigns. Route them through the broker or refuse their use when isolated execution is required.
2. Prototype the broker against disposable local sandboxes and synthetic campaigns. Verify concurrent and sequential read, write and process-interference denials, plus permitted artifact exchange. Exercise cancellation, crash recovery and teardown.
3. Add network default-deny enforcement and per-campaign policy before enabling arbitrary processes in the new sandbox. Verify DNS, redirect, IPv4, IPv6, proxy and infrastructure cases with mock services.
4. Migrate existing data without changing its ownership in place until a backed-up copy passes integrity and access checks. Preserve the current Docker Desktop deployment and signing keys. Provide a reversible switch and a documented rollback that does not delete volumes.
5. Enable the new boundary only after Bash, planner/worker, chat, custom tools, file tools, MCP and browser tests pass. Unsupported hosts and missing isolation features must fail closed, with an explicit operator-visible readiness error.

Changing only the global UID/GID, working directory or environment variables cannot satisfy this boundary. Until the broker is implemented and validated, ARTEX-001 and ARTEX-005 remain open and cross-campaign confidentiality and integrity must not be claimed.
