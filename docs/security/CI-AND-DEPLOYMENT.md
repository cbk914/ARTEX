# CI and deployment baseline

Source snapshot: `b9b2a7f`. The running Docker Desktop project was inspected read-only; no compose action, container replacement or volume migration was performed.

## CI inventory

`.github/workflows/ci.yml` has a pinned-Go job with PostgreSQL 16, `gofmt`, build, vet, serial `go test -p 1 ./...`, SQL script apply/rollback and a selected `go test -race` package list including `server`. A separate advisory job tests the latest stable Go. The workflow also has `govulncheck`, shellcheck and script tests, frontend TypeScript/test/static-build checks, and Python tests. The Go job uses suffixed test databases; two tests are documented as skipped in code pending issue #9. This describes CI configuration, not a verified result for this branch.

## Image and Compose inventory

`Dockerfile` pins the Node, Go, Debian, Python and PostgreSQL-related build inputs by image digest where shown, and pins Go 1.26.11. The runtime image declares volumes for `/app/data` and `/app/keys`; `start.sh` verifies the binary and restarts it after abnormal exits. The base `docker-compose.yml` binds `./data`, `./keys` and `./skills`, while PostgreSQL uses `pgdata`. The default published ports bind the API and proxy to loopback unless the operator changes `ARTEX_BIND_ADDR`. At the baseline snapshot neither checked-in Compose file defined an ARTEX container healthcheck. `server/ready.go` originally reported only PostgreSQL ping status with a short cache. The local remediation branch now also returns unready when the control-plane isolation self-test is explicitly degraded; it still does not attest campaign isolation.

On the local remediation branch, both checked-in Compose files now have an ARTEX healthcheck that calls `curl --fail --silent --show-error http://127.0.0.1:8787/api/ready`. `docker compose ... config --quiet` passed for each file, and this exact curl command returned `{"ready":true}` inside the existing running application container. A separately built branch image also returned the same response in a disposable fixture described below. A later synthetic pre-fix regression returned 200 when the isolation status was degraded and PostgreSQL was healthy; the corrected endpoint returns 503, while `/api/health` remains a liveness signal. Focused readiness race tests, vet and Windows cross-compilation passed. The endpoint does not gate on campaign isolation or migrations beyond startup behavior.

The running Docker Desktop project uses the named Linux volumes `artex_artex_data`, `artex_artex_keys`, `artex_artex_skills` and `artex_pgdata`. This differs from the base file's bind mounts. Its exact original Compose inputs and skill-volume update procedure remain to be verified.

`docker-compose.docker-desktop.yml` is a local overlay for the existing named-volume layout. With `docker compose -p artex -f docker-compose.yml -f docker-compose.docker-desktop.yml config --format json`, its four resolved volume names and destinations matched the running containers' read-only mount inventory. The project name matters: another name would create different volumes. This overlay does not copy data from the bind-mount profile and was not used to start or replace the running services. Before a future deployment, compare the effective Compose configuration and volume IDs again, back up the four volumes, and test migration and rollback on disposable volumes.

## Branch-image startup validation, 2026-11-27

`docker build --pull=false --progress=plain -t artex-galactus:security-validation-20261127 .` completed the full image from the remediation branch, including `npm ci` (zero reported advisories), static frontend export and the Go 1.26.11 binary. The image ID was `sha256:8f43824b586fc7b4c9f3606ed0e19c00ee22d3a11196c8c71ded9293be92dc56`. The local validation tag was removed after testing; no image was deployed.

A PostgreSQL 16 container and the branch app container ran on a disposable `--internal` Docker network. PostgreSQL data, `/app/data` and `/app/keys` were tmpfs; neither container had a bind or named volume, a published port or an operational credential. The first app fixture used Docker's default tmpfs permissions and failed its startup isolation self-test because UID 10001 could create a file in `/app/data`. This is the expected fail-closed behavior; the fixture was removed without using `-dev-insecure-no-isolation`. The second fixture used `--tmpfs /app/data:rw,size=256m,mode=0700,uid=0,gid=0` and the equivalent root-owned mode-0700 `/app/keys` tmpfs. Its isolation self-test passed, `schema_migrations` contained all 15 embedded migrations, both synthetic key files existed, `/api/ready` returned `{"ready":true}`, and UID 10001 could neither read the keys nor write the data root. The disposable containers, network and validation image were removed. The operational containers and named volumes were unchanged.

This validates a fresh startup with synthetic data only. The next section tests key reuse and rollback with dedicated volumes and a synthetic database. Migration of the existing named volumes, real operator login and broker-aware readiness remain open before any deployment.

## Synthetic upgrade and rollback validation, 2026-11-27

The currently deployed image ID `sha256:2876b75e32cfdd579f0e202639300ad703c746a05bf8203df77daf560ab89e7d` started against a new synthetic PostgreSQL 16 database and dedicated `artex-rollback-data-20261127` and `artex-rollback-keys-20261127` volumes. It applied migrations 1 through 14 and answered `/api/ready`. A synthetic marker was written under `/app/data/workspace`; SHA-256 fingerprints of its two generated keys were retained for comparison without disclosing key contents. The network was internal and neither app nor database published a port. PostgreSQL used tmpfs, not an operational volume.

The first branch image built from this Windows checkout failed closed against that database: the Docker context contained CRLF versions of the first 14 SQL migration files, while the deployed image recorded checksums of their LF Git blobs. All 14 old-image checksums matched the committed LF blobs. The SQL had not changed, but Go embedded the working-tree bytes. `.gitattributes` now fixes `db/migrations/*.sql` to LF, `TestEmbeddedMigrationsUseStableLF` checks the embedded bytes, and the Dockerfile stops a build if a migration contains CR. No migration SQL or database checksum row was edited to make the fixture pass. After rebuilding, the branch image started on the same synthetic volumes, applied migration 15, returned `/api/ready`, and preserved the marker and both key fingerprints.

Changing only the image back then failed closed: the previous binary rejected migration 15 because that file is absent from it. A second synthetic database exercised the supported rollback shape. After quiescing the old app at schema version 14, `pg_dump -Fc` created a readable pre-upgrade logical backup. The branch image advanced that fixture to version 15. After stopping it, the test restored the version-14 dump into **only that disposable database** with `pg_restore --exit-on-error`, started the previous image on the same data/key volumes, and observed `/api/ready`, schema version 14, and unchanged marker and key fingerprints. This verifies a synthetic backup-and-restore cycle, not an operational rollback or compatibility of real campaign data.

An operational change still requires verified backups of PostgreSQL and all four named volumes, exact image and Compose inputs, a data inventory, an operator-approved maintenance window, and a tested restore plan that preserves keys. A direct image-only rollback is incompatible once migration 15 has applied. No live container, credential or volume was changed in these tests.

A later local migration 16 stages network decision records. Its version-15-to-16 and complete database package tests passed on disposable PostgreSQL, but the full runtime image and operational rollback rehearsal above predate that migration. Repeat those gates for any candidate deployment image.

## Baseline test limits

The host Go 1.20.2 cannot parse the repository's Go 1.26.11 directive. The first disposable Go 1.26.11 container lacked PostgreSQL and had six root isolation test failures because the restricted UID could not execute Go's temporary test binary. A second disposable Go container and a PostgreSQL 16 container on an internal Docker network used a dedicated tmpfs database and a wrapper that made Go's temporary test binary traversable by that UID. That test-only wrapper is now preserved as `scripts/test-exec-isolation.sh`; from a disposable Linux test container, run `chmod 0700 scripts/test-exec-isolation.sh && go test -exec /src/scripts/test-exec-isolation.sh -p 1 ./...`. It changes permissions only on Go's temporary test binary and its two build directories, and does not relax ARTEX's isolation checks. `go test -exec /tmp/artex-test-exec.sh -p 1 ./...`, `go vet ./...`, and the CI-selected `go test -race` package list passed on the pre-ARTEX-011 code. Focused post-fix auth tests passed normally and under `-race`, and the full post-fix normal suite passed. The non-verbose runs did not enumerate test-level skips. Later frontend, Docker build, Compose and dependency checks are recorded in this file and the remediation state; their passing results do not establish browser acceptance or a safe operational deployment.
