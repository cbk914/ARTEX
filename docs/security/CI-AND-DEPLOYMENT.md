# CI and deployment baseline

Source snapshot: `b9b2a7f`. The running Docker Desktop project was inspected read-only; no compose action, container replacement or volume migration was performed.

## CI inventory

`.github/workflows/ci.yml` has a pinned-Go job with PostgreSQL 16, `gofmt`, build, vet, serial `go test -p 1 ./...`, SQL script apply/rollback and a selected `go test -race` package list including `server`. A separate advisory job tests the latest stable Go. The workflow also has `govulncheck`, shellcheck and script tests, frontend TypeScript/test/static-build checks, and Python tests. The Go job uses suffixed test databases; two tests are documented as skipped in code pending issue #9. This describes CI configuration, not a verified result for this branch.

## Image and Compose inventory

`Dockerfile` pins the Node, Go, Debian, Python and PostgreSQL-related build inputs by image digest where shown, and pins Go 1.26.11. The runtime image declares volumes for `/app/data` and `/app/keys`; `start.sh` verifies the binary and restarts it after abnormal exits. The base `docker-compose.yml` binds `./data`, `./keys` and `./skills`, while PostgreSQL uses `pgdata`. The default published ports bind the API and proxy to loopback unless the operator changes `ARTEX_BIND_ADDR`. At the baseline snapshot neither checked-in Compose file defined an ARTEX container healthcheck. `server/ready.go` reports PostgreSQL ping status with a short cache. Isolation status is exposed through the authenticated health response, but readiness does not currently require a successful isolation self-test.

On the local remediation branch, both checked-in Compose files now have an ARTEX healthcheck that calls `curl --fail --silent --show-error http://127.0.0.1:8787/api/ready`. `docker compose ... config --quiet` passed for each file, and this exact curl command returned `{"ready":true}` inside the existing running application container. A separately built branch image also returned the same response in a disposable fixture described below. The endpoint still checks PostgreSQL reachability only; it does not gate on isolation or migrations beyond startup behavior.

The running Docker Desktop project uses the named Linux volumes `artex_artex_data`, `artex_artex_keys`, `artex_artex_skills` and `artex_pgdata`. This differs from the base file's bind mounts. Its exact original Compose inputs and skill-volume update procedure remain to be verified.

`docker-compose.docker-desktop.yml` is a local overlay for the existing named-volume layout. With `docker compose -p artex -f docker-compose.yml -f docker-compose.docker-desktop.yml config --format json`, its four resolved volume names and destinations matched the running containers' read-only mount inventory. The project name matters: another name would create different volumes. This overlay does not copy data from the bind-mount profile and was not used to start or replace the running services. Before a future deployment, compare the effective Compose configuration and volume IDs again, back up the four volumes, and test migration and rollback on disposable volumes.

## Branch-image startup validation, 2026-11-27

`docker build --pull=false --progress=plain -t artex-galactus:security-validation-20261127 .` completed the full image from the remediation branch, including `npm ci` (zero reported advisories), static frontend export and the Go 1.26.11 binary. The image ID was `sha256:8f43824b586fc7b4c9f3606ed0e19c00ee22d3a11196c8c71ded9293be92dc56`. The local validation tag was removed after testing; no image was deployed.

A PostgreSQL 16 container and the branch app container ran on a disposable `--internal` Docker network. PostgreSQL data, `/app/data` and `/app/keys` were tmpfs; neither container had a bind or named volume, a published port or an operational credential. The first app fixture used Docker's default tmpfs permissions and failed its startup isolation self-test because UID 10001 could create a file in `/app/data`. This is the expected fail-closed behavior; the fixture was removed without using `-dev-insecure-no-isolation`. The second fixture used `--tmpfs /app/data:rw,size=256m,mode=0700,uid=0,gid=0` and the equivalent root-owned mode-0700 `/app/keys` tmpfs. Its isolation self-test passed, `schema_migrations` contained all 15 embedded migrations, both synthetic key files existed, `/api/ready` returned `{"ready":true}`, and UID 10001 could neither read the keys nor write the data root. The disposable containers, network and validation image were removed. The operational containers and named volumes were unchanged.

This validates a fresh startup with synthetic data only. It does not validate migration of the existing named volumes, persistent key reuse across replacement, compatibility with the previous image, rollback, real operator login or broker-aware readiness. Those gates remain open before any deployment.

## Baseline test limits

The host Go 1.20.2 cannot parse the repository's Go 1.26.11 directive. The first disposable Go 1.26.11 container lacked PostgreSQL and had six root isolation test failures because the restricted UID could not execute Go's temporary test binary. A second disposable Go container and a PostgreSQL 16 container on an internal Docker network used a dedicated tmpfs database and a wrapper that made Go's temporary test binary traversable by that UID. `go test -exec /tmp/artex-test-exec.sh -p 1 ./...`, `go vet ./...`, and the CI-selected `go test -race` package list passed on the pre-ARTEX-011 code. Focused post-fix auth tests passed normally and under `-race`, and the full post-fix normal suite passed. The non-verbose runs did not enumerate test-level skips. Later frontend, Docker build, Compose and dependency checks are recorded in this file and the remediation state; their passing results do not establish browser acceptance or a safe operational deployment.
