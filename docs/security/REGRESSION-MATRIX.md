## ARTEX-001/005 staged run directories

The disposable `scripts/test-sandbox-upload-volume.ps1` fixture tested a prospective attachment transport on Docker Desktop. It created two uniquely named test volumes, populated only A with a 17 MiB written file extended sparsely to 512 MiB, and mounted each volume read-only at `/campaign/main/uploads` beneath its sandbox's private `/campaign` tmpfs. UID 10001 in A read the marker and the final byte of the large file but could not write to the volume; B saw neither file and could not write. The fixture removed its test containers and volumes. This establishes nested mount feasibility and 512 MiB file addressability, not a 512 MiB transfer benchmark. At that stage, the broker had no upload-volume lifecycle implementation.

The broker derives a random campaign upload-volume name from its journaled sandbox spec, creates a local Docker volume with installation-owner and creation-token labels, and checks exact name, driver, scope, options and labels before removal. A newly created sandbox mounts it read-only at `/campaign/main/uploads`, under a separate executor-owned `/campaign/main` tmpfs. The broker attests the declared and effective mount and retains the journal record until container and volume removal complete. Recovery removes an orphaned owned volume and refuses a foreign one. Unit regressions cover foreign tokens and owners, unexpected labels and driver options, malformed specs, name collision, uncertain creation, retry after partial removal, read-only mount policy and orphan recovery. A packaged-broker Docker Desktop fixture passed two-campaign file-tool and artifact checks, distinct read-only upload mounts, explicit removal, sequential sandbox reuse and graceful cleanup.

The broker now accepts one stream up to 512 MiB through its root-only Unix API, bound to an opaque sandbox handle. A separate helper container with no network, dropped capabilities and no Docker socket mounts only that campaign's volume read-write. It stages the bytes under a root-private directory and checks exact length and SHA-256 inside the helper. A new name is published as a complete mode-0444 file through an exclusive hard link. A repeated name succeeds only when the existing file has the same length, digest and mode; different bytes cannot replace it. The broker removes the helper after the transfer, retires the sandbox on failure, and journal recovery checks for an interrupted helper before removing its volume. Unit tests cover malformed requests, a foreign helper and recovery order; the complete broker race suite and vet passed in a network-disconnected Go 1.26.11 container. A packaged-broker Docker Desktop fixture streamed a small synthetic file and an actual 17 MiB synthetic file to A, confirmed A could read but not write and B could not see the small file, accepted an identical retry, and rejected both changed bytes under the same name and a wrong digest with sandbox retirement. The fixture left no test containers or upload volumes. The 512 MiB maximum is enforced in code but has not been exercised end-to-end at that size. This remains a staged transport: operational ARTEX does not install the task sandbox controller, persistent storage quotas and real crash recovery remain unverified, and ARTEX-001/003/005 remain open.

The upload transport now accepts path-safe Unicode names up to 255 UTF-8 bytes, URL-escaping them in the client while rejecting separators, control characters and its private staging name. A real Docker fixture published and read `análisis final.txt` without losing the name. The task controller has a conditional `UploadAttachment` adapter that checks live task and exploration attribution and the task-deletion barrier before using its private broker handle; a synthetic race test and `go vet ./server` passed in the network-disconnected Go 1.26.11 container. Task chat now conditionally transfers validated attachments through this adapter. The HTTP task upload path and operational controller startup remain open.

The transport also accepts zero-byte attachments with the SHA-256 of empty content. The client checks that a source declared empty actually ends at EOF before sending a zero-length HTTP body; the helper still verifies size and digest before publishing. Focused HTTP, Unix client and Docker-engine tests and the complete broker race suite/vet passed in a disposable Go 1.26.11 container. The real Docker fixture published an empty synthetic file and read its zero length from the private sandbox. This preserves the existing upload handler's empty-file behavior; the operational task message path remains disconnected until controller startup is enabled.

The task controller derives `/campaign/main` or `/campaign/i<intentID>` from trusted run attribution for Bash, custom command/Python and file-tool calls. The file helper opens only the selected directory under the campaign-private root and rejects malformed directory names. A nested shell prevents a caller `||` branch from running when directory setup fails. `go test -race ./agent ./server -run "TestTaskSandbox|TestSandboxFile|TestCustom.*Sandbox|TestTaskBash" -count=1` and `go vet ./agent ./server` passed in a disposable, network-disconnected Go 1.26.11 image. A standard full-image build and `scripts/test-broker-docker-control.ps1 -FileToolSmoke` passed against two real disposable Docker sandboxes: main and worker files stayed separate in A, B could not see them, a blocked directory did not execute the caller command, and recreated A had neither file. The script removed its broker socket volume and containers. This is conditional source routing only; it does not demonstrate operational startup, top-level chat/MCP or interactive browser paths or a security boundary between agents of one campaign.

Task chat now acquires an exploration-bound interactive lease before any activity is emitted when the controller is installed. Paused or terminal tasks require that lease for main-agent tools, while planner and worker calls remain denied. Terminal sandbox retirement waits for the lease to end. The task chat attachment path reopens canonical uploads through `os.Root`, rejects changed or incompatible files, and sends their bytes through the broker before the main-agent turn. Focused race tests and vet passed in an isolated Go container; this server route has not been exercised against a live HTTP task with the controller installed. ARTEX-001/003/005 remain open.

## ARTEX-005 image environment admission

Docker image `ENV` entries are inherited by sandbox containers. A synthetic image with an added variable now fails broker admission before any sandbox exists; a real Docker-backed fixture confirmed HTTP 503, no sandbox container and cleanup of the broker socket volume. The reviewed current image still passed the two-campaign Docker fixture. Unit regressions reject an added image or container variable, a changed approved value, a duplicate and an image HOME override. The full `sandboxbroker` race suite and vet passed in a disposable Go 1.26.11 container without network. The first full-suite attempt failed because the test container lacked SETUID/SETGID for its peer-UID test; the retry with only those capabilities passed. This is an exact allowlist for the current digest-pinned image, not proof of operational ARTEX isolation or a credential injection design.

## ARTEX-010 broker aggregate quota

Pre-fix synthetic regressions confirmed that the ninth sandbox was created despite eight active ones and that a failed start plus failed Docker removal did not prevent another creation. `sandboxbroker.Broker` now caps active sandboxes at eight by default, accepts an explicit broker startup limit from 1 through 64, and denies further creation when Docker creation or failed cleanup leaves ownership uncertain. A 16-campaign concurrent admission regression confirms a configured limit of two admits only two; freed capacity can be reused after removal. The root-only broker can still run or remove already tracked sandboxes; restart performs its existing journal recovery before accepting work. The full Windows Go 1.26.11 broker suite passed with `-race`, vet passed, and the Linux broker entry point cross-built. The first race attempt failed before tests on an assembler/UNC temporary-path incompatibility; retrying with the mapped drive passed. This is a staged broker quota, not a production ARTEX resource limit. Docker-backed acceptance and operational host sizing remain pending.

## ARTEX-001/005 broker attestation hardening

A pre-fix synthetic inspect regression showed `DockerEngine.Verify` accepted host namespace modes, device access, supplementary groups, extra hosts, links, inherited volumes, port bindings and an added `seccomp=unconfined` security option. The fixed verifier rejects these deviations from the broker's fixed container policy. `go test -race ./sandboxbroker -count=1` and `go vet ./sandboxbroker` passed in a network-disconnected Go 1.26.11 container. A cross-compiled Windows test binary then passed the opt-in `TestDockerBrokerSmoke` against the local pinned ARTEX image on Docker Desktop and removed its disposable sandbox. No broker-labeled container remained. This is a safer host-side prototype, not deployed campaign isolation; ARTEX-001 and ARTEX-005 stay open.

The staged Linux broker control service accepts only create, run and remove on a Unix socket beneath root-controlled directories. Tests check opaque handles, strict/size-bounded JSON, method rejection, generic error responses, socket mode 0600, root client access, non-root peer rejection by `SO_PEERCRED`, registered-sandbox removal and socket removal on graceful shutdown. `go test -race ./sandboxbroker ./cmd/artex-sandbox-broker -count=1`, `go vet` for both packages and a Windows fail-closed cross-build passed in a network-disconnected Go 1.26.11 container. This remains unmounted in the operational ARTEX deployment; conditional task-tool routes exist in source but are not installed at startup, and broker crash recovery and user-namespace-remapped socket behavior are unverified.

`scripts/test-broker-cross-container.ps1` passed with the real `ServeUnix` listener and a fake engine in one Docker Desktop container and clients in separate disposable containers on a private named volume. The root client received a 64-character opaque handle. With test-only relaxed socket permissions, the UID-10001 client connected but was reset without an HTTP response; the fixture then verified graceful synthetic-sandbox removal and socket unlink. All labeled test containers and the volume were removed. This fixture observed cross-container socket semantics with a fake engine; the separate Docker-backed acceptance below exercises real engine calls.

`docker build --pull=false -f Dockerfile.broker -t artex-galactus:broker-validation-20261127 .` passed with a scratch final image containing only the CGO-free broker and the statically linked Docker CLI from a pinned official digest. `scripts/test-broker-docker-control.ps1` passed against the real Docker Engine: two synthetic campaigns were created through the root-only socket, one ran a command that verified neither control nor Docker socket was visible, both had `--network=none`, private tmpfs and no persistent mounts, one was removed by handle, and the other was removed on graceful broker stop. The broker fixture alone held the Docker socket; it had no network or writable root. Labeled test containers and the socket volume were absent afterward. The running ARTEX application still had no Docker socket mount. This is local broker acceptance, not an ARTEX executor-path test or deployment; ARTEX-001/005 remain open.

`sandboxbroker.Client` passed a Linux root-owned Unix socket create/run/remove cycle against the real local listener and fake engine. It rejected a missing socket, a mode-0666 socket, a symlink substituted for the socket and a retired handle; transport errors did not expose the handle. The client checks socket ownership and mode on every dial, cannot follow redirects or use a TCP proxy, and bounds response bytes. A separate regression showed that JSON encoding can expand a valid 64 KiB command past the former 128 KiB request cap; the 512 KiB cap admits that command while still rejecting oversized requests. `go test -race ./sandboxbroker ./cmd/artex-sandbox-broker -count=1` and `go vet` passed in a network-disconnected Go 1.26.11 container; the client also passed a Windows cross-build with non-Linux socket validation failing closed. No ARTEX task calls this client yet, so no campaign authorization or tool isolation is claimed.

The scratch broker image was rebuilt after this socket validator change and the real Docker-backed acceptance script passed again. The validation image was removed. Windows behavior remains cross-compiled and source-checked, without a runtime test.

The Docker adapter labels each child with both a per-container token and a broker owner. Unit regressions reject cleanup and policy verification when the owner differs, even with a matching token. `go test -race ./sandboxbroker ./cmd/artex-sandbox-broker -count=1`, `go vet` and Windows cross-compilation passed in an isolated Go image. The scratch broker image rebuilt and the Docker-backed acceptance passed with two child containers sharing the owner label; all disposable resources were removed. Linux broker startup persists and locks the owner. A root-only, fsynced write-ahead journal records the random name and token before Docker creation. Recovery tests reject malformed and foreign records and remove a stopped owned container only after full policy attestation. The disposable Docker crash-restart test removed a journaled orphan while preserving a foreign-labeled fixture; all fixtures were removed afterward. Handle recovery, arbitrary power-loss timing and production integration remain unproven.

## Cross-cutting global asset deletion authorization

Local remediation commit: `8634d12`.

`delete_assets_by_host` was bound to the Auto agent by default and used `AssetStore.DeleteByHost` directly. A synthetic pre-fix PostgreSQL regression showed a task-attributed tool call deleted one root domain and one child asset from the shared global library without operator authorization. The local guard removes its default binding and makes the legacy tool reject direct calls, including persisted bindings from prior databases. An authenticated `DELETE /api/assets/by-host` route preserves the operator's exact-host deletion operation and requires a second matching canonical host field. The ordinary auth middleware denies unauthenticated requests and foreign-origin cookie mutations. Focused post-fix normal/race tests and `go vet ./server` passed in a disposable Go 1.26.11 container with synthetic PostgreSQL 16. The complete server package suite passed with `go test -exec /src/scripts/test-exec-isolation.sh -p 1 ./server -count=1`; the two initial runs without that launcher failed only on six root isolation tests because Go's temporary binary directory was inaccessible to the dropped executor UID. This addresses only that global destructive tool; other agent-writable platform settings, skills and MCP definitions remain under review.

A separate pre-fix regression failed for all six persistence tools when the seeded approval rule was missing or disabled: `MatchPersistence` returned no decision and a target-only guard could allow the mutation. The fixed matcher returns a deny in that state, and a guard without any interceptor also blocks those tool names. Post-fix `go test -race -p 2 ./intercept ./guard -count=1` and `go vet ./intercept ./guard` passed in a disposable Go 1.26.11 container. Enabled ask rules and explicit deny rules retain their existing behavior. This covers agent tool calls through these guards, not arbitrary process writes to the same backing stores.

The diagnostic `server/executor_exposure_probe_linux_test.go` runs only with `go test -tags isolation_probe ./server -run TestSharedExecutorCrossCampaignExposureProbe -count=1 -v` in a disposable root-capable Linux container. It uses synthetic task directories, files and a sleep process. The 2026-11-27 run passed its **exposure** assertions: A read and replaced B's file, B read A's HOME marker after A's process ended, and A signaled B's process. This is evidence of the vulnerability, not a passing security acceptance test. The future campaign broker must replace these assertions with denial checks and add tests for each supported executor path.

The diagnostic `server/executor_network_probe_linux_test.go` runs only with `go test -tags isolation_probe ./server -run TestUnscopedExecutorCanReachLocalMockProbe -count=1 -v`. It uses `execPython` and a loopback-only TCP listener inside a disposable container with no external network. The 2026-11-27 run observed the unapproved custom-tool executor receive `PONG`. This confirms a missing independent network boundary for that route; it does not test every executor or prove any destination is authorized. See ADR 0003 for the complete enforcement and validation gates.

## ARTEX-012 validation and remediation

Root cause: `verifyJWT` accepted any HMAC signing method and did not require expiration, the ARTEX subject or an explicit `pwd` claim when the current version was zero. `jwtSubject` separately parsed the token with similarly broad rules. The pre-fix regression accepted all five malicious synthetic tokens (HS384, missing expiration, wrong subject, missing subject and missing password version). The current patch uses one parser with the JWT library's valid-method, expiration and subject options, and requires an explicit `pwd` equal to the current version. It preserves normal `signJWTVersion` tokens and the existing password-version test. Modified files: `server/auth.go`, `server/auth_jwt_strict_test.go`. Fix commit: `089299b`. Issuer and audience are not minted by this existing single-operator protocol and remain a future protocol decision. The browser still stores tokens in `localStorage` and accepts URL tokens; ARTEX-006 remains open.

Observed checks: focused regression and `TestPasswordVersionClaim` passed; `go vet ./server` and focused `go test -race` passed. The first container run passed with skips after six root isolation tests failed because the restricted UID could not execute Go's temporary test binary. A subsequent isolated Go 1.26.11 run against disposable PostgreSQL 16 passed `go test -exec /tmp/artex-test-exec.sh -p 1 ./...` with no command-line skips; the wrapper only made that temporary test binary accessible to the restricted UID. `go vet ./...` and the CI-selected `go test -race` package list passed on the pre-ARTEX-011 code. The non-verbose suites did not list test-level skips; CI documents two self-skipped tests. No deployment validation was performed.

## ARTEX-011 validation and remediation

Root cause: login validated the password against a database hash, then signed a token with the mutable in-memory password version. A barrier-controlled test forced a rotation between these steps and observed an old password mint a token at the new version. `db.GetAuthSnapshot` now reads hash and version in one PostgreSQL statement, so login signs only the version paired with the validated hash. In-memory version updates no longer regress when concurrent rotations finish their post-commit work out of order. Modified files: `db/settings.go`, `server/auth.go`, `db/settings_insert_test.go`, `server/auth_concurrency_test.go`, `server/login_limit_test.go`.

The focused normal and race-enabled tests for the login barrier, out-of-order version updates, database snapshot and existing auth/version cases passed against the disposable PostgreSQL database. The full post-fix `go test -exec /tmp/artex-test-exec.sh -p 1 ./...` suite passed after updating an existing test fixture to expect a 503 login response while its password-version row is deliberately corrupt, and successful login after repair. A concurrent rotation can still make a just-issued old-version token unusable; that is safe, but may require retrying login. Cross-process session revocation and the broader browser session design remain open under ARTEX-006. Fix commit: `deece11`.

## ARTEX-003 partial remediation

Root cause: `chatUpload` selected a free name with `Lstat`, then reopened it with `O_TRUNC`. Two uploads could select the same name and truncate each other's attachment. The synthetic pre-fix regression reproduced the duplicate selection. The local change opens the task or session run directory as an `os.Root`, creates and opens `uploads` through that root, and reserves each filename with `O_CREATE|O_EXCL` on a stable directory descriptor. It bounds the copy against parsed multipart size, checks cancellation and removes incomplete files. A link from the upload directory to a sibling campaign or outside the run root is rejected. Workspace uploads still intentionally overwrite existing names and are addressed separately under ARTEX-002.

Modified files: `server/chatupload.go`, `server/chatupload_name_test.go`, `server/chatupload_security_test.go`, `server/upload_symlink_test.go`. The focused normal and race tests, existing 512 MiB handler boundary test, and full PostgreSQL-backed `go test -exec /tmp/artex-test-exec.sh -p 1 ./...` suite passed in disposable Go 1.26.11 and PostgreSQL 16 containers. This does **not** complete ARTEX-003: attachments still become visible inside an agent-writable run directory, an agent can alter a completed attachment, and staging responses still carry absolute server paths. A protected staging store, immutable identifiers, finalization and controlled artifact exchange remain to be designed and tested. Partial mitigation commit: `22bf3f2`.

Chat message admission follow-up: the task and conversation handlers previously accepted client-supplied attachment `path`, `size` and `abs` metadata and passed the path to the agent message. They now resolve each attachment through that chat's `uploads/` root, reject traversal, links, nonregular files and mismatched size or digest, cap the attachment count and aggregate bytes, and replace client metadata with server-derived name, path, size and SHA-256. Task/session upload responses omit the absolute path; staging still returns one for the existing pre-task flow. Synthetic tests cover forged paths, sizes, digests, links and canonical metadata. The file can still change between validation and agent use because the run directory is writable by the executor; legacy metadata without a digest establishes only the current hash. Protected delivery remains necessary.

Workspace upload batch follow-up, commit `ecd3fe2`: a synthetic pre-fix request overwrote an existing first file, skipped a later `..` filename and returned success with `uploaded:1`. The handler now validates every filename and confined destination before replacing any file, then resolves again during each publication. It strips browser path components with either slash convention. The focused Windows Go 1.26.11 upload suite passed normally and under `-race`; `go vet ./server` passed. A late I/O failure or concurrent directory change after preflight can still leave earlier files published, so the multi-file request is not transactional. Protected staging and immutable attachment delivery remain open.

ARTEX-010 skill upload follow-up: `fsUploadSkill` had a 20 MiB request cap but did not use the shared multipart admission pool. It now returns 429 before reading the body when that pool is saturated and releases the slot on every exit. The synthetic test checks rejection before parsing and acceptance of a later malformed request as a normal 400. This bounds concurrent request parsing per process; disk, CPU, execution and campaign limits remain open.

Skill ZIP cancellation follow-up: the installer previously parsed and extracted a complete archive even when its request context had been cancelled. It now checks cancellation before admission, during compressed and extracted reads, between entries and before final installation; each copy is limited by the remaining aggregate quota, and close errors are handled before publishing. A regression submits a valid, pre-parsed ZIP with a cancelled context, checks that no skill or temporary file is installed, and confirms a later retry still works. The ordinary skill-upload suite, focused race run, vet and Windows cross-compilation passed. Crash-safe replacement of an existing skill and persistent storage quotas remain open.

ARTEX-007 local package-open follow-up: stored local archive paths were checked lexically and then reopened through `os.Open` for extraction; S3 upload also reopened the package by absolute path. The active restore and remote-upload paths now open the package directly under the private archive root, reject linked directories and nonregular or substituted files, and pass one descriptor through checksum verification, extraction or upload. Synthetic tests cover a final symlink, linked archive directory, nested path and post-open path replacement. Focused `go test -race ./server ./archivestore -run "TestOpenLocalTaskArchivePackage|TestS3|TestTaskArchivePackage|TestTaskArchive.*(Extract|RoundTrip)" -count=1`, vet and Windows server cross-compilation passed in a disposable Go 1.26.11 image without external networking. A writable root ancestor, in-place mutation of the opened inode, source/database generation consistency and deployment validation remain open.

ARTEX-007 extraction-root follow-up: source review found that `MkdirAll(destination)` followed by `OpenRoot(destination)` could accept a linked final destination and unpack outside the intended restore directory. Extraction now opens the final directory from its protected parent, rejects a link, and compares the inspected and opened directory identities. A synthetic linked-root test includes an outside sentinel; Windows skips that test because directory symlinks require unavailable privilege. The focused archive suite passed normally and under `-race` with Go 1.26.11 on Windows, and `go vet ./server` passed. Linux linked-root execution, parent ancestry protection and operational restore validation remain open.

ARTEX-001/010 terminal-capacity follow-up: a new task sandbox request now retires tracked sandboxes whose task is terminal, deleted or bound to a different exploration before broker creation. It serializes with operations on each retired sandbox, preserves active and paused sandboxes, and denies creation when a status lookup or removal fails. Synthetic controller tests passed under `-race` with Go 1.26.11 on Windows, and `go vet ./server` passed again after the admission edit. A terminal-task admission now attempts removal before reviving the task and leaves it terminal on failure. The PostgreSQL-backed revival test was skipped on Windows because no test database is configured; that admission ordering is source-reviewed, not dynamically verified.
